동작 방식

기능 명세(.md)를 넣으면 QA 양식 테스트 케이스(.xlsx)가 나옵니다.

1. 입력기능 명세(.md) 작성
→
2. 요소 추출규칙과 수치 범위, 상태 전이 식별
→
3. 케이스 도출정상·경계·예외 각 1건 이상
→
4. 출력TC 시트와 명세 이슈 시트

명세에서 입력 필드와 동작 규칙, 수치 범위, 오류 메시지, 상태 전이를 읽어내고 규칙마다 케이스를 만듭니다. 요소 파악부터 집계까지를 자동화하되, 커버리지와 기대 결과의 최종 검토는 사람이 맡도록 범위를 정했습니다.

실제 TC 샘플

슬레이 더 스파이어 전투 시스템 명세에서 생성한 66건 중 유형별로 한 건씩 가져왔습니다.

TC-01 턴 구조 전투 시작 시 플레이어 선공 정상 EP 전투 진입 직후 적이 먼저 행동하지 않고 플레이어 턴부터 시작
TC-04 턴 구조 적 턴 도중 마지막 적 처치 → 즉시 승리 경계 ST 적 턴 중 반사 피해 등으로 마지막 적 체력 0 적 턴 도중이라도 즉시 전투 승리, 남은 적 행동 취소

우선순위 열은 지면 관계로 생략했습니다. 예외는 High, 경계는 Medium, 정상은 Low로 자동 부여됩니다.

명세 이슈

테스트 케이스를 만들다 보면 명세의 빈틈이 드러납니다. 위치·문제·제안 세 열로 정리해 별도 시트에 남깁니다.

위치문제제안
§6 공격 피해 계산 (다단 히트) 1번은 '타격당 피해 = 기본 + 힘'만 규정하고 2·3번(약화·취약 배수)이 히트 단위인지 합계 단위인지 불분명 '2·3번 배수는 각 히트의 피해에 개별 적용한다'처럼 히트 단위 적용을 명시
§7 취약/약화/손상 감소 시점 '대상 또는 보유자의 턴 종료 시 1 감소'로만 되어 있어 적이 보유한 디버프의 감소 시점이 모호 적 보유 디버프는 '적 턴 종료 시' 감소한다고 별도 문장으로 고정
§5·§7 배수 계열 노드 구성 배수(%) 노드가 몇 종인지, 각 노드의 최대 레벨과 버킷 상한이 명시되지 않음 노드 종류 수와 노드별 최대 레벨, 상한 도달 설계 의도를 명시

명세 3건에서 결함 16건을 찾았습니다. 테스트 케이스를 쓰려면 기대 결과를 확정해야 하는데, 확정할 수 없는 지점이 곧 기획서의 구멍입니다. 코드가 나오기 전에 기획 단계에서 잡아낼 수 있는 결함입니다.

생성 규칙

자동화의 품질은 규칙이 결정합니다. 아래 기준을 문서로 고정해 두고 생성합니다.

케이스 도출

  • 정상·경계·예외를 각 1건 이상 — 셋 중 하나라도 빠지면 표를 완성하지 않습니다.
  • 수치 범위는 네 지점 — 하한-1 / 하한 / 상한 / 상한+1을 각각 케이스로 만듭니다.
  • 상태 전이는 양방향 — 허용 전이와 금지 전이를 각각 케이스로 만듭니다.
  • 예외의 정의 — 규칙 위반, 필수 누락, 형식 오류, 상태·권한 위반.
  • 한 행에 한 케이스 — 여러 케이스를 한 셀에 합치지 않습니다.

분류 기준

  • 기법 — EP(동등 분할) · BVA(경계값 분석) · DT(결정 테이블) · ST(상태 전이) 중 적용한 것을 표기합니다.
  • 우선순위 — 예외는 High, 경계는 Medium, 정상은 Low로 자동 부여합니다.
  • 상태 — Pass / Fail / Blocked / N/A / Not Run 목록 제약을 걸고 기본값은 Not Run입니다.

지어내지 않기

  • 명세에 없는 수치·메시지·규칙을 사실처럼 적지 않습니다.
  • 추정이 불가피하면 해당 셀에 [가정]을 붙여 표시합니다.
  • 명세의 모순과 누락은 지어내서 메우지 않고 Spec Issues 시트에 기록합니다.
  • 기대 결과는 구체적 값으로 적고 "정상 동작" 같은 모호한 표현을 쓰지 않습니다.
